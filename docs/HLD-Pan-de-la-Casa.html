El documento distingue siempre dos escenarios:

  • MVP: lo que está desplegado hoy en Azure for Students, al costo más bajo posible.
  • Producción: la arquitectura objetivo que cumple todos los requisitos no funcionales y que se costea en docs/costs/.

1. Contexto del negocio y alcance

El negocio. Pan de la Casa es una panadería de barrio con un solo local. Vende amasijos, panes y dulces del día. Hoy los pedidos llegan por teléfono o en persona. El cliente no sabe si lo que quiere sigue disponible, y en la hora de más venta hace fila para pagar algo que pudo dejar pedido. Los fines de semana la demanda se triplica (3x).

Qué resuelve el sistema. El cliente consulta desde el celular el catálogo con fotos y precios, arma su pedido y elige a qué hora lo recoge. Recibe un código corto que dice en la tienda. La panadería ve los pedidos del día organizados por hora de recogida y prepara solo lo pedido.

Actores.

Actor Qué hace Estado
Cliente Consulta el catálogo y registra pedidos. No crea cuenta. MVP
Administrador de la panadería Ve los pedidos del día, cambia su estado y edita el catálogo desde un panel. Planeado
Equipo de desarrollo Cambia el código y el catálogo por pull request; aprueba el paso a producción. MVP

Alcance.

Incluye
MVP (desplegado) Catálogo con fotos y precios · carrito · pedido con hora de recogida y código · dos ambientes (dev y prod) · pipeline con pruebas, smoke test y rollback · logs, métricas y alerta
Producción (diseñado) Todo lo anterior con SLA · panel del administrador con inicio de sesión · API con identidad administrada · secretos en Key Vault · fotos en Blob Storage
Fuera del alcance Pagos en línea (se paga al recoger) · domicilios · inventario y producción · cuentas de cliente · notificaciones por correo o WhatsApp

Reglas de negocio del pedido (en src/api/src/lib/orders.js, con pruebas unitarias):

  • La recogida es entre las 07:00 y las 19:00, hora de Colombia.
  • Se pide con al menos 30 minutos de anticipación y como máximo 7 días antes.
  • Máximo 20 productos distintos y 50 unidades por producto.
  • Los precios salen del catálogo en el servidor, nunca del navegador: un cliente no puede cambiar el total.
  • Un producto marcado como no disponible no se puede pedir.

3.2 MVP (desplegado)

El MVP usa la misma forma con planes gratuitos:

  • Static Web Apps Free con managed functions: la API viene incluida en la Static Web App, sin Function App aparte.
  • Las fotos se sirven desde la propia Static Web App (src/web/img/).
  • No hay panel de administrador: el catálogo se cambia por pull request.
  • Hay un recurso de Static Web Apps por ambiente (swa-pandelacasa-dev y swa-pandelacasa-prod).
  • Dev y prod comparten una cuenta de Cosmos DB, con una base de datos por ambiente de 400 RU/s cada una.
  • Toda la infraestructura está en infra/main.bicep y la crea el pipeline.

Diferencias entre MVP y producción, y por qué:

Aspecto MVP Producción Motivo del cambio
Plan de Static Web Apps Free Standard El Free no tiene SLA
API Managed functions Function App propia Identidad administrada y triggers no HTTP
API → Cosmos DB Clave en la configuración Identidad administrada con RBAC Quitar la última clave (ADR-003)
Fotos En la Static Web App Blob Storage Subirlas desde el panel
Panel de administrador No Sí, con Entra ID RF-5 y RF-6

3.3 Flujo de un pedido y escalado ante el 3x

  1. El navegador descarga la página desde Static Web Apps, que la sirve como contenido estático sin consumir cómputo.
  2. La página pide GET /api/products. La API responde desde una caché de 30 s; si la caché está vencida, lee el catálogo en Cosmos DB (2,5 RU).
  3. El cliente envía el pedido a POST /api/orders. La API valida los datos, recalcula precios y total con el catálogo, genera el código y guarda el pedido (12,76 RU) en la partición de su fecha de recogida.
  4. La API responde con el código, el total y la hora de recogida.

Capacidad. Prod tiene 400 RU/s. Con 12,76 RU por pedido, eso alcanza para unos 31 pedidos por segundo sostenidos. Un sábado de producción (+50 %) tiene unos 135 pedidos; aunque llegaran todos en la misma hora serían 135 × 12,76 / 3600 ≈ 0,5 RU/s, el 0,1 % de la capacidad. Las lecturas del catálogo no crecen con las visitas, porque cada instancia de la API lo lee como máximo una vez cada 30 s. El 3x de los fines de semana queda muy por debajo del techo. Si se alcanzara, la API responde 503 con un mensaje para reintentar, la alerta avisa (§6) y prod puede subir a 600 RU/s sin salir del free tier (ADR-002).

Escalado del cómputo. Static Web Apps sirve el contenido estático sin límite de instancias que administrar, y Functions agrega instancias según las peticiones. No hay que configurar reglas de autoescalado ni encender nada antes del fin de semana.

4. Seguridad e identidad

4.1 Transporte y navegador

  • Static Web Apps solo sirve HTTPS. Cosmos DB exige TLS 1.2 como mínimo (minimalTlsVersion).
  • staticwebapp.config.json envía cabeceras de seguridad en todas las respuestas:
    • Content-Security-Policy: script-src 'self', connect-src 'self' y sin estilos ni scripts en línea.
    • X-Frame-Options: DENY, contra el clickjacking.
    • X-Content-Type-Options: nosniff.
    • Referrer-Policy.
  • La página no carga nada de terceros: las fuentes y las fotos se sirven desde el propio sitio.

4.2 Identidades

Quién Cómo se autentica Qué puede hacer
Cliente Anónimo Leer el catálogo y crear pedidos
Administrador (planeado) Microsoft Entra ID con la autenticación de Static Web Apps; rol admin Rutas /admin y /api/admin/*, restringidas por rol en staticwebapp.config.json
Pipeline (GitHub Actions) OIDC: token de corta duración, aceptado solo desde los environments dev y prod del repositorio, que solo aceptan despliegues desde main Contributor solo sobre rg-pandelacasa
API → Cosmos DB, MVP Clave maestra de la cuenta en la configuración de cada Static Web App, escrita por Bicep Leer y escribir en las dos bases (dev y prod): la clave es de la cuenta, no de una base (riesgo R5)
API → Cosmos DB, producción Identidad administrada de la Function App con un rol de datos de Cosmos DB Solo los contenedores de su base; la autenticación por clave queda desactivada

4.3 Secretos y mínimo privilegio

  • No hay ningún secreto guardado en GitHub para entrar a Azure (OIDC, ADR-003).
  • El token de despliegue de Static Web Apps y la clave de Cosmos DB se piden en cada ejecución del pipeline y se enmascaran en los logs.
  • El repositorio y los logs de Actions son públicos. Por eso el correo de alertas va como secreto de GitHub (ALERT_EMAIL) y ningún archivo contiene IDs de suscripción ni de tenant.
  • La rama main está protegida: solo entra por pull request con las pruebas y la validación de IaC en verde, sin excepción para los administradores, y el despliegue a prod exige aprobación manual. Los environments dev y prod solo aceptan despliegues desde main.
  • Riesgo aceptado en el MVP: Checkov reporta 3 hallazgos sobre Cosmos DB (acceso público y autenticación por clave). Están justificados en docs/despliegue.md, con lo que cambia en producción.

4.4 Datos personales (Ley 1581 de 2012)

Un pedido guarda el nombre y el teléfono del cliente, que son datos personales. Medidas:

  • Datos mínimos: solo los necesarios para entregar el pedido. No hay cuentas, correos ni direcciones.
  • Fuera de los logs: la API registra el código, la cantidad de productos y el total, nunca el nombre ni el teléfono.
  • Cifrado: viajan por HTTPS. Cosmos DB los guarda cifrados en reposo de forma predeterminada.
  • Pendiente para producción:
    • un aviso de privacidad y una casilla de autorización en el formulario, como exige la ley;
    • un tiempo de vida (TTL) en el contenedor orders, para que los pedidos se borren solos pasado el plazo que defina la panadería.

5. Disponibilidad, respaldo y recuperación

5.1 Disponibilidad

El requisito es 99,5 % en horario comercial: 12 h × 30 días = 360 h al mes, con un margen de 1,8 h (108 minutos) de caída al mes.

El MVP no puede prometerlo, porque el plan Free de Static Web Apps no tiene SLA. Por eso producción usa Standard. Para atender un pedido intervienen tres servicios en serie. Sus SLA, según el documento oficial de Microsoft Service Level Agreements for Online Services (versión del 17 de noviembre de 2026), son:

Servicio en la ruta del pedido SLA
Static Web Apps (Standard) 99,95 %
Azure Functions (plan Consumption) 99,95 %
Cosmos DB, una región sin zonas de disponibilidad 99,99 %
Compuesto (0,9995 × 0,9995 × 0,9999) 99,89 %

99,89 % sobre un mes completo (730 h) equivale a unos 48 minutos de caída al mes en el peor caso. Aunque todos cayeran en horario comercial, quedan por debajo de los 108 minutos permitidos.

Quedan fuera de la cuenta:

  • Key Vault: la API lee los secretos al arrancar.
  • Blob Storage: sin fotos, el catálogo y los pedidos siguen funcionando.
  • Application Insights: no está en la ruta del pedido.

Una sola región. Todo corre en Central US, la única región permitida por la suscripción donde existe Static Web Apps. Una caída regional completa es un riesgo aceptado (§7): una segunda región duplicaría el costo para un negocio con un solo local.

5.2 Respaldo

Qué Cómo se recupera
Pedidos (orders) Respaldo continuo de Cosmos DB, 7 días, restauración a cualquier segundo (ADR-004)
Catálogo (products) Se recarga desde data/catalog.json en cada despliegue
Infraestructura infra/main.bicep: el pipeline la recrea
Código y configuración Git en GitHub; cada despliegue registra su commit en version.json

5.3 RPO y RTO

Requisito Diseño
RPO 24 h Cosmos DB copia cada cambio al respaldo en menos de 100 segundos: en el peor caso se pierden unos 2 minutos de pedidos.
RTO 4 h Restauración autoservicio por portal o CLI, sin ticket de soporte. Medido el 19 nov: la cuenta restaurada estuvo lista en 10 min 33 s y los pedidos volvieron en unos 12 minutos (docs/despliegue.md).

El procedimiento paso a paso (congelar despliegues, restaurar, copiar los pedidos a la cuenta original y verificar con el smoke test) está en ADR-004.

Escenario Respuesta
Un despliegue rompe el sitio Rollback automático al último commit bueno. Probado el 17 nov: dev volvió sola en menos de 3 minutos y prod no se tocó (docs/despliegue.md).
Se borran o dañan pedidos Restaurar a un punto anterior al error y copiar los pedidos con scripts/restore-orders.js (ADR-004, paso 3). Probado el 19 nov: un pedido borrado volvió idéntico.
Se borra una base o un contenedor Restauración dentro de la misma cuenta (ADR-004, paso 2).
Se borra el grupo de recursos scripts/bootstrap.sh y el pipeline recrean la infraestructura en minutos. Para los pedidos se evalúa restaurar la cuenta borrada desde su respaldo continuo, antes de volver a correr el pipeline (si no, el pipeline crea una cuenta vacía con el mismo nombre). No está probado.

6. Observabilidad y operación

6.1 Qué se recoge

Señal Dónde Configuración
Peticiones a la API (ruta, código, duración) Application Insights → Log Analytics (AppRequests) Un Application Insights por ambiente. En dev se muestrea el 50 % de la telemetría
Logs de la API AppTraces Errores de Cosmos DB y un registro por pedido, sin datos personales
Métricas de la plataforma Application Insights y Cosmos DB Peticiones, errores, RU consumidas, peticiones con 429
Versión desplegada /version.json Commit, ambiente y si fue un rollback

Log Analytics conserva 30 días con un tope de ingesta de 1 GB al día, para que un error que inunde los logs no dispare el costo. La telemetría llega en los dos ambientes: verificado el 18 de noviembre en AppRequests.

6.2 Alertas

Alerta Condición A quién avisa
Errores de servidor Al menos una respuesta 5xx de la API en 5 minutos. Severidad 1 en prod, 3 en dev Correo del equipo
Presupuesto Gasto real > 50 % o pronóstico > 100 % de USD 20 al mes Correo del equipo

La alerta cuenta las respuestas por código HTTP, no la métrica de "peticiones fallidas". Verificamos en AppRequests que Functions marca como exitosa toda respuesta que no lanza una excepción: los 400 del smoke test llegan con Success = True. Con la métrica de fallidas, un 503 por Cosmos DB caído o saturado no habría avisado.

6.3 Operación

  • Verificación de cada despliegue: el smoke test comprueba que se sirve el commit correcto, que /api/health responde, que el catálogo trae productos y que un pedido inválido se rechaza. Con un pedido inválido no se crean pedidos falsos en producción.
  • Consultas útiles en Log Analytics:
    • errores de la última hora: AppRequests | where TimeGenerated > ago(1h) and toint(ResultCode) >= 500 | summarize count() by Name, ResultCode;
    • pedidos registrados hoy: AppTraces | where Message startswith "Pedido" | summarize count() by bin(TimeGenerated, 1h).
  • Procedimientos:
    • rollback: docs/despliegue.md;
    • restauración de datos: ADR-004;
    • configuración inicial: scripts/bootstrap.sh.
  • Responsables: el equipo recibe las alertas por correo. En horario comercial, una alerta de severidad 1 se revisa en menos de 30 minutos.

7. Riesgos y mitigaciones

Probabilidad e impacto: A = alto, M = medio, B = bajo.

# Riesgo Prob. Impacto Mitigación
R1 El MVP corre en el plan Free, sin SLA. M M Producción usa Standard con SLA (§5.1). El MVP no promete el 99,5 %.
R2 Pedidos falsos en masa: POST /api/orders es público y no limita peticiones por cliente. M M Límites por pedido (20 productos, 50 unidades). El tope de 1000 RU/s hace que un abuso termine en errores 503, no en una factura, y la alerta avisa. En producción: límite de peticiones por IP en la API y, si el abuso se repite, Azure Front Door con WAF (costo aparte).
R3 Datos personales sin aviso de privacidad ni autorización (Ley 1581). A M Datos mínimos, fuera de los logs y cifrados (§4.4). Antes de abrir al público: aviso, casilla de autorización y TTL en orders.
R4 El panel del administrador no está construido. A B Mientras tanto, el catálogo se cambia por PR y los pedidos se consultan en Cosmos DB. Diseño definido en §4.2.
R5 Clave maestra de Cosmos DB en la configuración de las dos Static Web Apps (MVP). Es de la cuenta compartida: un error en el código de dev, que se despliega sin aprobación, podría leer o cambiar los pedidos de prod. B A Nunca está en el repo ni en los logs; dev solo se despliega desde main, después de las pruebas; la identidad del pipeline solo alcanza el grupo de recursos. En producción, identidad administrada con un rol de datos limitado a su base y autenticación por clave desactivada (ADR-003).
R6 Cosmos DB con acceso de red público (MVP). B M TLS 1.2, clave requerida, Checkov documentado. En producción se evalúa un endpoint privado (docs/despliegue.md).
R7 Caída de la región Central US. B A Riesgo aceptado: una segunda región duplica el costo. La infraestructura es código y se puede recrear en otra suscripción.
R8 Se superan las 400 RU/s en un pico. B M Caché del catálogo y capacidad medida (§3.3). Prod puede subir a 600 RU/s sin costo (ADR-002).
R9 Un despliegue defectuoso llega a producción. M A Pruebas que bloquean el merge, smoke test en dev, aprobación manual y rollback automático probado.
R10 Pérdida o daño de pedidos por error humano o de código. B A Respaldo continuo de 7 días con restauración autoservicio (ADR-004).
R11 Volver a respaldo periódico con git revert bloquea el pipeline. B M El cambio es irreversible en Azure y está advertido en Bicep y en ADR-004.
R12 La suscripción de estudiante agota sus créditos o vence. B A Presupuesto con avisos; el MVP cuesta casi cero. La infraestructura es código y se recrea en otra suscripción con bootstrap.sh.
R13 El rollback automático solo vuelve a desplegar la app. Los cambios de Bicep (configuración, alertas, Cosmos DB) y del catálogo se aplican antes del despliegue y quedan aplicados aunque el smoke test falle. B M Bicep es declarativo: un cambio de infraestructura que rompa se revierte con git revert y merge, que vuelve a aplicar la versión anterior. El caso del catálogo está documentado en docs/despliegue.md (sección Catálogo).
R14 La API no tiene lockfile propio: el build de Static Web Apps instala @azure/functions y @azure/cosmos con rangos ^ en cada despliegue, y un rollback puede instalar versiones más nuevas que las que funcionaban. B M El smoke test detecta una API rota y el pipeline no promueve a prod. Pendiente: versionar src/api/package-lock.json; en producción, desplegar la Function App como paquete construido en el pipeline.
R15 Dev y prod comparten la cuenta de Cosmos DB y Log Analytics: un despliegue de dev y uno de prod de ejecuciones distintas pueden actualizarlas a la vez. B B La concurrencia es por ambiente. Si Azure rechaza uno por una operación en curso, falla sin cambios y se reintenta con "Re-run failed jobs".

ADR-001: Azure Static Web Apps con Azure Functions para el sitio y la API

  • Estado: aceptado
  • Fecha: 2026-11-18

Contexto

Pan de la Casa necesita un sitio público con el catálogo (fotos y precios) y una API para registrar pedidos con hora de recogida. La carga es pequeña y desigual: entre semana hay poco tráfico, los fines de semana se triplica (3x) y de noche casi no hay visitas.

Requisitos que pesan en la decisión:

  • Costo: máximo USD 150/mes en producción, y el MVP debe costar lo mínimo posible.
  • Escalar ante el 3x de los fines de semana sin intervención manual.
  • HTTPS obligatorio.
  • 99,5 % de disponibilidad en horario comercial.
  • Región: la suscripción Azure for Students solo permite centralus, brazilsouth, canadacentral, westus y westus3.
  • Equipo: dos estudiantes, sin tiempo para administrar servidores.

Alternativas

  1. Azure App Service (plan Linux) con la app web y la API en el mismo servidor. Ventajas: modelo conocido, una sola aplicación, sin límites de tipo de trigger. Desventajas: se paga el plan las 24 horas aunque no haya visitas; el autoescalado solo existe desde el plan Standard, así que cubrir el 3x sin intervención exige un plan de pago desde el primer día. HTTPS y dominio se configuran aparte.
  2. Azure Container Apps con un contenedor que sirve el sitio y la API. Ventajas: escala a cero y escala por demanda. Desventajas: hay que escribir y mantener un Dockerfile, un registro de imágenes y la configuración de ingreso, solo para servir un catálogo y un formulario. El frontend estático pasaría por el mismo contenedor que la API.
  3. Azure Static Web Apps (frontend) con Azure Functions (API). Ventajas: el frontend se sirve desde la red global de Static Web Apps con HTTPS incluido; la API corre en Functions, que escala sola y no cobra cuando no hay tráfico; el despliegue desde GitHub Actions viene integrado. Desventajas: en el plan Free las funciones son "administradas": solo admiten triggers HTTP, no tienen identidad administrada y el plan no tiene SLA.

Decisión

Opción 3: Static Web Apps + Azure Functions, en dos niveles:

  • MVP (lo desplegado): Static Web Apps Free con managed functions (Node.js 22, Functions v4), un recurso por ambiente (swa-pandelacasa-dev y swa-pandelacasa-prod) en Central US, la única región permitida por la suscripción donde existe Static Web Apps.
  • Producción (lo que se costea): Static Web Apps Standard con una Function App propia enlazada (bring your own functions). El plan Standard es el que tiene SLA y el único que permite enlazar una Function App propia, y esa Function App sí admite identidad administrada (ver ADR-003).

Es la opción que cubre el 3x sin configurar nada, cuesta casi cero cuando no hay tráfico y no deja servidores que administrar.

Consecuencias

  • Costo: el MVP no paga hosting (plan Free). En producción se paga el plan Standard más el consumo de la Function App; el detalle está en docs/costs/.
  • Escalado: el frontend estático no consume cómputo; la API escala con Functions. La caché de 30 s del catálogo en la API evita que cada visita del pico lea la base de datos.
  • Disponibilidad: el plan Free no tiene SLA, así que el MVP no puede prometer el 99,5 %. Por eso producción usa Standard. El cálculo de disponibilidad está en el HLD.
  • Arranque en frío: la primera petición después de un rato sin tráfico tarda más en responder. Para una panadería es aceptable, y el smoke test lo tolera con reintentos.
  • Solo HTTP en el MVP: tareas programadas (por ejemplo, un resumen diario de pedidos) necesitan la Function App propia de producción.
  • Dependencia de la región: si Static Web Apps dejara de estar disponible en Central US para la suscripción, habría que cambiar de suscripción, no solo de región.

ADR-002: Azure Cosmos DB for NoSQL con free tier para catálogo y pedidos

  • Estado: aceptado
  • Fecha: 2026-11-18

Contexto

El sistema guarda dos tipos de datos:

  • Catálogo: 9 productos en 3 categorías. Se lee en cada visita y cambia poco (un precio, un producto nuevo).
  • Pedidos: documentos de ~1 KB con nombre, teléfono, productos, total y hora de recogida. Se escriben uno a uno y la panadería los consulta por día de recogida.

Requisitos: costo mínimo en el MVP y menos de USD 150/mes en producción; soportar el 3x de los fines de semana; respaldo con RPO 24 h y RTO 4 h; dos ambientes (dev y prod) aislados; y una región permitida por la suscripción (Central US).

Alternativas

  1. Azure SQL Database (serverless). Ventajas: modelo relacional, consultas SQL completas, el equipo lo conoce. Desventajas: hay que diseñar y migrar un esquema para datos que son documentos simples; en modo serverless la base se pausa sin tráfico y la primera petición después de la pausa espera a que reanude, justo cuando llega el primer cliente del día.
  2. Azure Table Storage. Ventajas: muy barato y sin capacidad que administrar. Desventajas: solo guarda propiedades planas (los productos de un pedido tendrían que serializarse a mano) y las consultas son limitadas. No tiene restauración a un punto en el tiempo como Cosmos DB.
  3. Cosmos DB for NoSQL en modo serverless. Ventajas: se paga por operación, sin capacidad fija. Desventajas: el free tier no aplica a cuentas serverless, así que toda operación se cobra.
  4. Cosmos DB for NoSQL con throughput aprovisionado y free tier. Ventajas: el free tier regala 1000 RU/s y 25 GB de por vida de la cuenta; los pedidos se guardan como el mismo JSON que usa la API, sin esquema que migrar; latencia baja y estable; respaldo continuo con restauración a un punto en el tiempo (ADR-004). Desventajas: solo una cuenta con free tier por suscripción, y la capacidad aprovisionada es un techo que hay que vigilar.

Decisión

Opción 4: Cosmos DB for NoSQL con free tier, configurado en infra/main.bicep:

  • Una cuenta con free tier y un tope de throughput de 1000 RU/s en la cuenta, para que nunca se cobre capacidad por encima de lo gratuito.
  • Una base por ambiente, panaderia-dev y panaderia-prod, con 400 RU/s compartidas cada una (800 de las 1000 gratuitas). Dev nunca escribe en los datos de prod.
  • Contenedor products con clave de partición /category: el catálogo se lee completo y se agrupa por categoría.
  • Contenedor orders con clave de partición /pickupDate (fecha de recogida en hora de Bogotá): la consulta principal de la panadería es "los pedidos de hoy", que así se resuelve dentro de una sola partición.

Consecuencias

  • Costo: USD 0 en el MVP mientras se respeten los 1000 RU/s y los 25 GB. Con pedidos de ~1 KB, los 25 GB alcanzan para millones de pedidos.
  • Capacidad ante el 3x: las 400 RU/s de prod son un techo fijo. La API guarda el catálogo en caché 30 s, así que las visitas del pico casi no leen la base; el consumo real lo concentran las escrituras de pedidos. Si el techo se alcanzara, Cosmos DB responde 429 y la API responde 503 con un mensaje para reintentar; cualquier respuesta 5xx dispara la alerta. Si hiciera falta, prod puede subir a 600 RU/s (parámetro databaseThroughput) y seguir dentro de los 1000 gratuitos (400 de dev + 600 de prod).
  • Una sola cuenta para dos ambientes: los cambios de configuración de la cuenta (como el respaldo) afectan a dev y prod a la vez y se aplican con el despliegue a dev.
  • Autenticación por clave en el MVP: las managed functions no tienen identidad administrada, así que la API usa la clave de la cuenta, inyectada por Bicep en la configuración de Static Web Apps (nunca en el repositorio). En producción se reemplaza por identidad administrada (ADR-003).
  • Dependencia del proveedor: el SDK y el modelo de RU son propios de Azure. El riesgo es bajo porque los datos son JSON plano y la API accede a ellos a través de una interfaz pequeña (listProducts y saveOrder), fácil de reimplementar sobre otra base.

ADR-003: OIDC para el pipeline y manejo de secretos

  • Estado: aceptado
  • Fecha: 2026-11-18

Contexto

El pipeline de GitHub Actions crea la infraestructura con Bicep y despliega la app en Azure, así que necesita credenciales de Azure. La API, a su vez, necesita acceso a Cosmos DB.

Requisitos: secretos fuera del código y mínimo privilegio. El repositorio y los logs de Actions son públicos, así que cualquier secreto que se filtre en un archivo, un commit o una salida del pipeline queda expuesto para siempre.

Alternativas

  1. Service principal con secreto de cliente guardado en los secretos de GitHub. Ventajas: es el método clásico y funciona en cualquier sistema de CI. Desventajas: el secreto vive en GitHub, vence y hay que rotarlo; si se filtra, sirve desde cualquier lugar hasta que alguien lo revoque.
  2. Token de despliegue de Static Web Apps guardado como secreto de GitHub (lo que genera la plantilla por defecto). Ventajas: cero configuración. Desventajas: es un secreto de larga duración; solo sirve para subir la app, así que igual se necesita otra credencial para Bicep.
  3. OIDC (credenciales federadas) con una identidad administrada de Azure. Ventajas: no hay ningún secreto guardado. En cada ejecución, GitHub emite un token de corta duración que Azure acepta solo si viene de este repositorio y de un environment concreto. Desventajas: la configuración inicial es más larga (identidad, credenciales federadas, asignación de rol).

Decisión

Opción 3: OIDC con la identidad administrada id-pandelacasa-github, creada por scripts/bootstrap.sh:

  • Credenciales federadas solo para los environments dev y prod del repositorio. Hay 4: dos con el formato de nombres (repo:<owner>/<repo>:environment:<env>) y dos con el formato de IDs inmutables, que es el que GitHub emite hoy en el subject del token.
  • Rol Contributor solo sobre el grupo rg-pandelacasa, no sobre la suscripción.
  • El token de Static Web Apps no se guarda: el pipeline lo pide en cada ejecución con la identidad OIDC y lo enmascara en los logs. Lo mismo con la clave de Cosmos DB que usa la sincronización del catálogo.
  • La clave de Cosmos DB de la API la escribe Bicep directamente en la configuración de Static Web Apps; nunca pasa por el repositorio ni por los logs.
  • El correo de alertas va como secreto de GitHub (ALERT_EMAIL), porque el repositorio es público.

En producción, la API corre en una Function App propia (ADR-001) con identidad administrada y acceso a Cosmos DB por RBAC, sin clave. Los secretos que queden (por ejemplo, de un proveedor externo) van en Key Vault, y la autenticación por clave de Cosmos DB se desactiva.

Consecuencias

  • Nada que rotar ni que se pueda filtrar desde GitHub. Un fork o un PR no obtiene acceso a Azure: Azure solo acepta tokens de los environments dev y prod de este repositorio, y los dos environments solo aceptan despliegues desde ramas protegidas, es decir, desde main (que exige PR con CI en verde, también para los administradores). prod además exige aprobación manual.
  • Radio de impacto limitado: si el pipeline se compromete, solo puede tocar el grupo de recursos del proyecto.
  • En el MVP queda una clave de Cosmos DB en la configuración de Static Web Apps, porque las managed functions no tienen identidad administrada. Por eso Checkov reporta "autenticación local habilitada"; es un riesgo aceptado del MVP que desaparece en producción.
  • Contributor es amplio dentro del grupo: puede crear y borrar cualquier recurso del grupo. Un rol a medida sería más estricto, pero no se justifica para un grupo que solo contiene este proyecto.

ADR-004: Respaldo continuo de 7 días en Cosmos DB

  • Estado: aceptado
  • Fecha: 2026-11-17

Contexto

El enunciado exige RPO 24 h (perder como máximo un día de pedidos) y RTO 4 h (volver a operar en menos de 4 horas). Los datos que importan están en Cosmos DB: el catálogo se puede recrear desde data/catalog.json, pero los pedidos solo existen en la base.

La cuenta se creó con el respaldo periódico: una copia cada 4 h y 8 h de retención (las dos copias gratuitas). Eso cumple el RPO, pero tiene dos problemas:

  • Restaurar requiere abrir un ticket a soporte de Azure. El tiempo de respuesta no depende de nosotros, así que no podemos garantizar el RTO de 4 h. Además, el equipo no quiere depender de soporte para operar.
  • Solo hay 8 h hacia atrás. Un error que se descubra al día siguiente (por ejemplo, un cambio que borra pedidos un viernes en la noche y se nota el sábado) ya no se puede recuperar.

Restricciones: suscripción Azure for Students (sin plan de soporte de pago), presupuesto de USD 150/mes en producción y el mínimo costo posible en el MVP.

Alternativas

  1. Mantener el respaldo periódico (cada 4 h, 8 h de retención). Ventajas: ya está configurado y es gratis. Desventajas: restaurar exige un ticket a soporte (RTO fuera de nuestro control) y la ventana de 8 h es corta. Subir la retención genera cobro por copia adicional.
  2. Respaldo continuo de 7 días (Continuous7Days). Ventajas: restauración autoservicio (portal o CLI) a cualquier segundo de los últimos 7 días; el almacenamiento del respaldo no tiene costo en este nivel; las bases o contenedores borrados se pueden restaurar dentro de la misma cuenta. Desventajas: cada restauración cuesta USD 0,15 por GB restaurado; el cambio desde periódico es irreversible; una restauración completa crea una cuenta nueva.
  3. Respaldo continuo de 30 días (Continuous30Days). Igual que la opción 2 con más historial, pero cobra el almacenamiento del respaldo por GB al mes. Una semana es suficiente para detectar un error en una panadería que opera todos los días.
  4. Exportación propia programada (un workflow nocturno que lee los contenedores y guarda JSON en Blob Storage). Ventajas: sin soporte y con retención a elección. Desventajas: es código y almacenamiento que hay que mantener y proteger, el RPO sería de 24 h justas y restaurar implica escribir y probar un script de importación.

Decisión

Opción 2: respaldo continuo de 7 días. Es la única que cumple RPO y RTO sin depender de soporte ni agregar costo fijo. Se configura en infra/main.bicep (backupPolicy.type: 'Continuous', tier: 'Continuous7Days') y se aplica con el pipeline, como el resto de la infraestructura.

Con esta decisión:

  • RPO: Cosmos DB copia cada cambio al respaldo de forma asíncrona, en menos de 100 segundos. En el peor caso se pierden unos 2 minutos de pedidos, muy por debajo de las 24 h exigidas.
  • RTO: una restauración completa crea una cuenta nueva; tarda más cuanto más datos haya, pero con los datos actuales (menos de 1 MB) casi todo el tiempo es crear la cuenta. Medido en un simulacro el 19 nov: la cuenta restaurada estuvo lista en 10 min 33 s y los pedidos volvieron a la cuenta original en unos 12 minutos (detalle en docs/despliegue.md).
Procedimiento de restauración

El pipeline siempre apunta a la cuenta original (su nombre es fijo en Bicep) y en cada despliegue recrea panaderia-<ambiente>, products y orders. Por eso los datos vuelven a la cuenta original y no se reapuntan las apps a mano: el siguiente despliegue desharía ese cambio.

  1. Congelar despliegues: no hacer merge a main hasta terminar. Un despliegue recrearía los contenedores vacíos y ocuparía los nombres que se quieren restaurar.
  2. Si se borró una base o un contenedor: restaurarlo en la misma cuenta, al instante anterior al borrado (az cosmosdb sql database restore o az cosmosdb sql container restore). Las apps no cambian.
  3. Si se borraron o dañaron pedidos (los contenedores siguen existiendo): restaurar la cuenta a una cuenta temporal, al instante anterior al error (az cosmosdb restore), copiar los documentos de orders de vuelta a la cuenta original con scripts/restore-orders.js y borrar la cuenta temporal. El catálogo no hace falta: el pipeline lo recarga desde data/catalog.json.
  4. Verificar con el smoke test y reanudar los despliegues.

Consecuencias

  • Costo: USD 0 al mes por el respaldo. Una restauración de los datos actuales (menos de 1 MB) cuesta menos de un centavo. La cuenta temporal del paso 3 no tiene free tier (la suscripción solo admite una cuenta con free tier), así que cobra su throughput a precio normal mientras exista; por eso se borra apenas termina la copia.
  • No hay vuelta atrás al modo periódico, y Azure rechaza cualquier despliegue que lo intente. Revertir este cambio con git revert bloquearía el pipeline: si alguna vez hubiera que deshacer el PR, se conserva el bloque backupPolicy. Lo aceptamos porque el modo continuo es superior en todo lo que nos importa.
  • El cambio se aplica con el despliegue a dev, antes de la aprobación de prod, porque dev y prod comparten la cuenta de Cosmos DB. La aprobación de prod no lo frena: la decisión se toma al aprobar este PR.
  • La migración corre en segundo plano. Mientras no termine, Azure puede rechazar otro despliegue sobre la cuenta. Hay que aprobar prod solo cuando la migración figure como completada (az cosmosdb show --query backupPolicy.migrationState).
  • El respaldo vive en la misma región (Central US). Una caída regional completa no está cubierta: es un riesgo aceptado para una PyME con un solo local, que se registra en la tabla de riesgos del HLD.
